# Maintaining this fork

This repository is a maintained fork of [Boobaw/dsh-telegram-bot](https://github.com/Boobaw/dsh-telegram-bot). It adds:

- `/new`: a fresh session in the same topic and workspace.
- User-created topics: each new topic asks for its workspace and a new or existing session; `/workspace` switches; topic names are never changed after session titles.
- Two-way sync on by default: `mirrorTurns` is upstream's option, but the fork defaults it to on (upstream: off), so turns started in the Web UI, by scheduled tasks or by other plugins also appear in the bound topic.
- Sending into topics by thread id: the `telegramTopics` Host service, the `telegram_send` tool and the `dsh-telegram-send` command, with the sender (job, session) recorded and remembered, so replies to those messages carry the full original. Every send, the bound session's own included, is recorded in the bound session as a `user/message` (source kind `telegram-post` with the sender and the topic as `principal`, the text only what was sent; before 0.9 a `telegram-post:` request id, which the mirror skips) with its pictures, files and sticker image as attachments, because DSH has no non-model entry a plugin may append (new event types make a session unreadable) and a plain user message is what the Web UI draws with images. `recordMessage` appends it to an idle session and queues it otherwise.
- Web client (`src/client.js`, copied to `client.js`): the Telegram settings page, and a Chat Definition that claims only pre-0.9 send records (`kind: 'user'`, `telegram-post:` request id) and hands them to DSH's own notice row. Records with a `principal` are drawn by dsh-message-context's client, which keys on the principal for every producer; Chat allows one claim per message, so this client must not claim them too.
- Sessions the bot creates are never left blank (DSH's New conversation would reuse them): see `claimForTopic` in `src/app.js`.
- Session titles are `Telegram-<person>-<DSH title>` (`plannedTitle` in `src/topics.js`): DSH has no title hook, so `syncTopicTitle` re-appends each generated `session/title` with the prefix and the same source (automatic titling keeps running), and `startTopicTitle` calls `sessionTitle.refresh` at the first model request, because the `Telegram-<person>-<topic name>` placeholder is a user title that stops automatic titling. `<person>` comes from `userNames` / `userNamesFile`, else the chat's Telegram name (`chatNames` in the state file, learned from messages or `getChat`). Each session record keeps the label its title carries (`titlePerson`), so a changed name still finds the old prefix. A changed label reaches a session's title the next time the session is used. DSH's session header keeps only its own fields (dsh-session copies `cwd`, `parentSession`, `agentPreset` and the rest by name), so the source and person are not in session meta; DSH 0.2.2 has experimental plugin records (`appendPluginRecord` in dsh-session) that could carry them in the log later. Topic renames record a `telegram-topic` notice as a `user/message` (`recordNote`): session search indexes only message, tool and todo events, not titles or queued inbox items.
- Deleted topics are forgotten as soon as any Bot API call reports them gone (`forgetGoneTopic`).
- Chat-wide commands sent in All are answered in All; the topic Telegram made for them is deleted.
- Sender and message metadata (`src/sender.js` for the Telegram principals, the tagger in `@soffits/dsh-channel-core`): each Telegram prompt records who wrote it as `source.principal` and when it was sent (Telegram's `date`, or `edit_date` for an edit) and what it replies to or forwards as `source.envelope`, the contract of dsh-message-context, which renders it for the model; the text stays as sent. The zone also goes on the prompt as `clientTimeZone`, DSH's field for the zone of the person behind a prompt, so time-context reads in it instead of telling the model to ask; prompts the bot builds itself carry a `telegram:<chat>:<message>` request id for the same reason (time-context reads the zone only from user prompts with one). DSH writes `principal` itself only for non-owner callers of its session controller, and the bot hands text prompts to that controller, which builds the message, so the bot remembers the sender and envelope by request id and records them on the message in an `agent/pre-step` listener registered without `prepend` (a prepended renderer then sees them); messages the bot builds itself get them directly. Sends recorded in a bound session carry the sender (job, session or label) the same way.
- Voice messages, audio and round videos: downloaded, transcribed (DSH speech-to-text or a configured command, through `@soffits/dsh-channel-core`) and passed with their file path.
- Messages sent during a running turn are steered into it (`src/steer.js`): text through `sessionController.prompt({ mode: 'steer' })`, the Web UI's own call, and prompts with stored attachments through `agent.steer`, the method that mode uses. DSH keeps the turn going while its next-step inbox holds input and starts a new turn when input is left after `turn/end`, so a message that lands as the turn ends is still answered; `chat.steerFollow` shows that turn in the topic even with `mirrorTurns` off, and is cleared at the first `turn/end` that leaves the inbox empty. Prompts reach DSH in order (`admitInOrder`). `busyMessages: queue` keeps upstream's bot-side queue.
- Stickers: received ones are attached as images (thumbnail or first frame for animated and video stickers) and kept in a library (`src/stickers.js`) with the agent's meaning notes; the `telegram_sticker` tool finds, views, notes, loads sets and sends them through `sendToTopic`.
- Goal rounds use upstream's `adoptGoalTurn` path (thinking, tools, answer and the goal panel, also with `mirrorTurns` off), for goals started or driven from the topic (`goalOrigins` in the state file); other goals' panels are cleared from the topic. The Host-wide mirror can see a goal round's `turn/start` before its goal prompt; `adoptGoalTurn` then takes the turn over, so it is shown once.
- Models (`@soffits/dsh-channel-core`, with Telegram's callback keys and pages in `src/models.js`): the session's agent owns its model (`agent.model.current()`); the bot keeps no copy, because a copy drifted on fallback switches and Web UI picks and was carried into `/new`. Sessions are created and resumed through `sessionController.create` / `resolveAgent` (the Web UI's own composition); the raw `agents` registry is only the headless fallback. The picker reads `sessionController.modelCatalog()` and applies picks to the session only (`selectSessionModel`): the Web picker's `sessionController.selectModel` also saves the default for new sessions. `/new` starts the new session on the previous session's current model.
- Lifecycle notices go to a chat fixed by config (`controlChatOf` in `src/utils.js`: `controlChat`, else the first allowed user's private chat). Upstream moves its control chat to whoever wrote last and stores it in `topics.json`; the fork dropped that file.
- Final replies keep only the answer (`answerSegments`, `cutSilent` in `@soffits/dsh-channel-core`): text written between tool calls streams as a live draft, but at the turn's end the reply is rebuilt from the session's durable messages, keeping the last text block of each message that called no tool. Mirrored turns use the same rule. A message sent into the running turn after it started replying (Telegram steer, Web, schedule: `isInterjection`) splits the reply where DSH records it (`splitAnswer`): the reply message above keeps the answers given before it, or is deleted when there were none, and the live reply, thinking and tool messages start again below it, so a reply never lands above the message it answers. Web and scheduled messages are mirrored when they enter the inbox (`agent/inbox/spliced`), not when the agent takes them at its next step, and their later `user/message` is skipped by id.
- Subagent activity (`src/agents.js`): `subagent/start` and `subagent/end` (global listeners) drive one status card per topic, found by following `session.header.parentSession` from the child up to a bound session. A card opens only while the topic shows a turn (`busy` and not `done`); while it lists running subagents every new one joins it, from any turn, and nested children are listed under their parent. While anything runs the card stays the topic's last message: Telegram has no bottom pin (a pin sits at the top and posts a service message), so, like the sticky-message bots, it is sent again silently and the old copy deleted once a message lands below it. Every send goes through `call`, which reports the new message ids (`noteSent`), and `handleMessage` reports incoming ones; message ids grow within a chat, so a higher id in the same topic means the card is no longer at the bottom. Edits and moves are coalesced (1.5 s) and serialized per card, a running card ticks once a minute but edits only when the text changes, and a card whose children are all done is frozen where it is. The description is the parent catalog's `label` (the delegation's `description`), read again at each edit until found. `/agents` walks `subagents.listChildren` (durable catalogs, bounded reads) and reads each child's `subagentTiming` and `modelSelection` projections and its log for the last `send_message` or tool-free answer.
- Reply, quote and forward context (`src/message-context.js`): what a message replies to, quotes or forwards goes in `envelope.replyTo` / `envelope.forwardedFrom` (upstream writes it into the prompt text instead); forwards sent together become one prompt.

Upstream changes are merged in, not rebased, so the history of both lines stays intact.

## Merging upstream

```bash
git remote add upstream https://github.com/Boobaw/dsh-telegram-bot.git   # once
git fetch upstream
git switch main
git merge upstream/main
npm install
npm test
git push origin main
```

Conflicts usually land in `src/app.js` (most of the bridge lives there), `README.md` and the `name` and `version` lines of `package.json`. Keep the fork's own name and version: it is published on npm as `@soffits/dsh-telegram-bot` with its own semver line (0.4.0 was the first release, on top of upstream 0.3.0), so bump the minor version for features and upstream merges and the patch version for fixes, and name the merged upstream version in the merge or release commit. Make sure `client.js` still matches `src/client.js` after the merge (`cmp client.js src/client.js`).

Fork-only code is kept in separate files where that is natural (`src/topics.js`, `src/outbox.js`, `src/message-context.js`, `src/sent-log.js`, `src/voice.js`, `src/steer.js`, `src/sender.js`, `src/clock.js`, `src/models.js`, `src/agents.js`, `bin/dsh-telegram-send.js`, `test/fake-dsh.js`, `test/fork-features.test.js`, `test/message-context.test.js`, `test/sent-log.test.js`, `test/steer.test.js`, `test/sender.test.js`, `test/clock.test.js`, `test/models.test.js`, `test/agents.test.js`, `test/voice.test.js`), so most upstream edits apply without touching it.

Logic the fork shares with soffits/dsh-matrix-bot lives in the `@soffits/dsh-channel-core` package (soffits/dsh-channel-core): the final answer of a turn and `[SILENT]`, session models and the catalog, voice transcription, and the sender principal, envelope and tagger. A fix to that logic goes there, then a dependency bump here; `src/app.js` only imports it.
